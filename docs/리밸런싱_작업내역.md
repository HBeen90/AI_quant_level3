# 1부. 디벨롭 — 새로 만든 것

## 1-1. 버퍼 발동 진단 (`buffer_binding`)

**해결한 문제**: `policy_comparison.csv`의 네 정책이 소수점 끝까지 같은데,
이것이 (a) 코드가 정책을 안 읽는 버그인지 (b) 표본 안에서 버퍼가 발동할 기회가
없었던 정상인지 표만 봐서는 구분되지 않았다.

**만든 것**: `src/rebalance.py`에 `buffer_binding()` 신설. 기존 종목 중
"신규였다면 못 들어왔을 값인데 기존이라 남은" 관측을 직접 센다.

```
binding = (value < entry_threshold) AND (value >= hold_threshold)
```

- 앵커 제외 (규칙0으로 판정하므로 임계값 무관)
- 핵심은 `exposure`, 위성은 `mem_ratio`로 판정 지표 분기
- 하드 탈락(`eligible=False`)은 버퍼가 못 구하므로 집계 제외
- `select_v2()` 반환에 동봉해 상위 계층이 집계 가능

**연결**: `analysis/run_backtest.py`에 `buffer_binding_history()`를 만들어
정기변경 시점별로 집계하고, `policy_table()`에 **`버퍼발동 건수`** 열을 추가.
`out/backtest/buffer_binding.csv`로 저장. 0건이면 해석 주석을 출력한다.

이제 표가 스스로 말한다. 발동 0건이면 동일 결과가 정상이고, 0이 아닌데 행이
같으면 그때 배선을 의심하면 된다.

## 1-2. 독립 진단 스크립트 (`analysis/buffer_binding_report.py`)

가격 데이터도 백테스트 엔진도 없이 **스냅샷만으로** 돌아간다. 세 가지를 낸다.

## 2-2. KIND 증거 수집기 해시 불일치

`analysis/collect_kind_admin_history.py`의 sha256이 매니페스트 기록값과 달랐다.

```
현재(CRLF, 22,169B) : 9cbbe048…
LF 변환(21,592B)    : 6564ea5f…  ← 매니페스트와 일치
```

`.gitattributes`의 `*.py text eol=lf`가 이 파일 체크아웃 이후에 추가돼,
저장소에는 LF인데 작업 사본만 CRLF였다. **증거가 틀린 게 아니라 파일이 기록된
형태와 달라진 것**이므로 매니페스트가 아니라 파일을 되돌렸다.

## 2-3. 클레임 검증 순환 덫 (구조적)

```
테스트 실패 → 클레임 FAIL → FACTSHEET에 [FAIL] 기록
→ test_claims가 "FACTSHEET에 FAIL 없음"을 검사하다 실패
→ 테스트 실패 (원점)
```

한 번 걸리면 원인을 다 고쳐도 스스로 풀리지 않는다.

설계자는 알고 있었다 — `test_claims.py`가 기대 목록에서 자기참조 클레임을
제외하고, 팩트시트 생성에 `--fast`를 쓴다. 그런데 `run_backtest_final.ps1`
6단계만 `--fast` 없이 부르고 있었다.

**조치**: 6단계를 6a(테스트 관문 분리) / 6b(FACTSHEET `--fast` 생성)로 분리.

## 2-4. FINAL 매니페스트 자기무효화 (가장 구조적)

`_final_manifest_valid()`가 매니페스트 커밋과 현재 HEAD의 **동일성**을 요구했다.
그런데 확정 실행 7단계가 산출물을 동결 커밋하므로, **성공한 실행이 마지막
단계에서 스스로 HEAD를 옮겨 방금 만든 매니페스트를 무효로 만들었다.**

수치가 풀린 상태가 동결 커밋 직전 한 순간에만 존재했고, 그 뒤 누가 검증하든
항상 '잠정'으로 돌아가 있었다. 몇 번을 다시 돌려도 같은 자리에서 잠겼다.

**조치**: 판정 기준을 '커밋 동일'에서 **'코드 무변경'**으로 교체.

```python
if _code_changed_between(manifest_commit, _git_head()):
    return False
```

7단계가 stage하는 경로(`data/snapshots`, `out/`, `docs/FACTSHEET.md`)는 코드와
겹치지 않으므로 동결 커밋은 통과하고, 코드가 한 줄이라도 바뀌면 무효가 된다.
임시 저장소로 4개 경우를 검증했다.

| 상황 | 결과 |
|---|---|
| 동일 커밋 | 유효 |
| 산출물만 동결 커밋 후 | **유효** ← 풀려야 했던 것 |
| 코드 변경 커밋 후 | 무효 (보호 유지) |
| 알 수 없는 커밋·오류 | 무효 (fail-closed) |

데이터 무결성 검사(입력·스냅샷·산출물 해시 대조)는 손대지 않았다.

# 3부. 규명한 사실 6건

## 3-1. 버퍼는 표본 안에서 한 번도 발동하지 않았다

4정책 × 13시점 = **발동 0건**. 원인은 편출이 6년간 0건이라는 데 있고, 그 원인은
편입 7종목의 판정값이 **전 구간 단조 비감소**라는 데 있다.

> **함정 하나**: 한미반도체의 0.80 → 0.60은 하락이 아니다. 위성군일 때는
> 메모리향비중, 핵심군으로 올라선 뒤에는 HBM노출도로 판정하므로 **지표가
> 갈아끼워진 것**이다. 숫자만 이으면 승격을 하락으로 읽는다. 같은 군이 이어진
> 구간 안에서만 비교하도록 진단 코드를 짰다.

반증 실험에서 1%p 충격만으로 정책이 갈라진다. 규칙은 살아 있고, 조용했던 것은
표본이다.

## 3-2. 27/67의 근거는 실측이 아니라 합성 민감도다

`analysis/sensitivity_v2.py`(seed 11개)에서 회전율 0.377 → 0.268(29% 감소).
스크립트 자체가 "합성이므로 정책 간 차이만 유효"라고 명시하고 있다.

**"실측 회전율을 보고 골랐다"고 말하면 `policy_comparison.csv`를 여는 순간
무너진다.**

## 3-6. 잠정 매니페스트의 계보가 끊겨 있었다

정정 전         [3,3,3,3,3,3,3,3,4,4,6,7,8]
