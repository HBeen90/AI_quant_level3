## 1. 배당 / PR·TR — 절반 맞음, 개념 하나는 정정 필요

### 이미 있었던 것

`simulate_index(mode="gross_tr", ordinary_dividends=...)`가 이미 구현돼
있었습니다. 배당락일 세전 재투자(`r = Δp/p + dps/p_prev`), 비중 drift는
가격 수익률만 사용(배당은 바스켓에 비례 재투자되므로 상대비중에 중립),
PR↔TR 이중반영 가드까지 들어 있습니다.

### 정정이 필요한 개념

> "배당락일 시 가격 낙폭이 지수 손실로 **잘못 기록**됩니다 … 지수 착시"

**가격지수(PR)에서 배당락 하락은 오류가 아니라 정의입니다.** PR은 배당을
제외한 가격 변동만 측정하므로, 배당락 하락을 반영하는 것이 정상 동작입니다.
KRX·FnGuide의 대다수 테마지수 기본 계열도 PR입니다. 고칠 대상이 아니라
**TR을 별도 계열로 병기할** 대상입니다. 어느 쪽을 공식 지수로 삼을지는
위원회 결정 사항입니다.

이걸 "버그"로 규정하면 조문이 흔들립니다 — 방법론 4장 산식은 PR 정의를
그대로 따르고 있고, 그건 맞게 쓰여 있습니다.

### 추천 코드의 부호 규약 주의

```js
return B_t * (M_t - totalDividendsKW) / M_t;   // 리뷰 제안
```

수식 자체는 맞지만 **`M_t`가 배당락 직전인지 직후인지에 따라 답이 달라집니다.**
엔진은 배당락일 **종가**만 갖고 있어서 `M`은 이미 하락이 반영된 값입니다.
그 상태에서 위 식을 그대로 쓰면 배당분이 두 번 빠집니다.

그래서 부호 규약을 명시적으로 고정했습니다:

```python
def adjust_divisor_for_dividend(B_t, M_ex, dividend_M):
    """M_ex = 배당락일 종가 기준 비교시가총액(하락 이미 반영)
       dividend_M = Σ IIF_i × FF_i × S_i × DPS_i  (양수)
       B(t+1) = B(t) × M_ex / (M_ex + dividend_M)"""
    return B_t * M_ex / (M_ex + dividend_M)
```

`M_pre = M_ex + D`를 대입하면 리뷰 식과 동일합니다. 어느 표기를 쓰든 상관
없지만, **어느 쪽인지 코드에 적어두지 않으면 반드시 사고가 납니다.**

### 실제로 한 일

정기·수시에서 했던 것과 같은 방식으로, TR도 **두 독립 경로가 일치함을
실증**했습니다(`tests/test_tr_equivalence.py`):

```
[OK] 대조 A: 제수 기반 TR == 수익률 기반 TR (최대 상대차 2.56e-15)
[OK] 대조 B: 배당락일 PR 954.86 < TR 965.47 (상쇄폭 1.1110%) — PR 하락은 정의상 정상
[OK] 대조 C: 누적 TR/PR = 1.021593014 (독립 손계산 1.021593014)
[OK] 대조 D: PR↔TR 이중반영 가드 3종 작동
```

대조 C는 엔진을 안 쓰고 IIF 정의부터 손으로 다시 계산해 맞춘 것입니다.

`run_backtest.py`에 `--mode both --dividends <CSV>`를 추가해 PR·TR을
병기하고 연환산 배당 기여도를 냅니다. 스모크 실행 결과:

```
                    PR          TR
CAGR          0.166254    0.176344
MDD          -0.133096   -0.123421
연율화회전율(편도)  0.217344    0.217344   ← 회전율은 동일(당연)
  연환산 배당 기여도(TR - PR) = 0.8651%
```

**남은 공백은 수학이 아니라 데이터입니다.** 배당 CSV(`ex_date, ticker, dps`)
계약을 정의하고 거래일 아님·음수·특별배당 혼입을 fail-closed로 막아 뒀습니다.
pykrx의 `DPS`는 연간 추정 스냅샷이라 배당락일을 역산하기 위험하므로,
**DART 「현금·현물배당결정」 공시의 배당기준일**을 원천으로 쓰기를 권합니다
(이미 `OpenDartReader`를 쓰고 있으므로 경로가 열려 있습니다).

## 2. 월말 30% 캡 — 이미 구현되어 있고 테스트도 있습니다

리뷰의 문제 인식(한미반도체형 폭등)은 정확하지만, 그 대응은 이미 코드에
있습니다. 리뷰가 제안한 의사코드와 **기존 구현이 사실상 같습니다**:

```python
# backtest.build_event_schedule (기존 코드)
if vm is not None and bool(is_month_end.loc[d]):
    recheck_and_book_cap(i)        # monitor() → 30% 초과 시 25% 목표 → D+2 예약
```

`vm.drift(rets.loc[d])`가 매일 호출되므로 드리프트는 상시 추적됩니다.
기존 테스트도 있습니다 — `test_schedule_v2.py`의 "월간 캡 30%→25% D+2 집행",
"정확히 D+2 거래일" 검증.

**5배 폭등 시나리오 재현 결과** (`audit_review_claims.py`):

```
시나리오: 핵심1이 400거래일 동안 5배 상승, 정기변경은 최초 1회뿐
생성된 이벤트: 총 4건 (regular 1, cap 3)
  2026-05-04  최대비중 0.2500
  2026-07-02  최대비중 0.2500
  2026-12-02  최대비중 0.2500

[대조] 캡을 껐을 때 단일 종목 최대비중: 47.66%
       캡을 켰을 때                    : 25.00%
```

리뷰가 우려한 "45% 이상으로 치솟는" 상황이 대조군에서 실제로 재현되고
(47.66%), 캡이 그걸 25%로 눌렀습니다. **이미 작동 중입니다.**

### 그런데 진짜 공백이 있습니다 — 버킷 레벨 드리프트

리뷰의 "**40:60 비율 구조를 크게 침범**"이라는 표현은 타당한데, 그건
개별 캡으로 안 잡힙니다. 같은 시나리오에서:

```
앵커 합계 : 40.00% (정기변경일) → 34.14% (기말)
위성 합계 :  6.49%              →  5.26%   (조문상 상한 18%)
최대 단일 : 27.11%  (개별 캡 30% 이하로 잘 유지됨)
```

**개별 종목은 30% 아래인데 앵커 버킷이 40% → 34.14%로 밀렸습니다.**
`monitor()`/`cap_algorithm()`은 개별 종목만 보고, 앵커 40% 고정과 위성 합계
18% 상한은 **정기변경 시점에만** 적용됩니다.

이건 조문 개정 사안입니다. 엔진이 임의로 버킷 리밸런싱을 넣으면 방법론에
없는 매매가 발생하고 회전율이 바뀝니다. **순서는 진단 → 계측 → 위원회
상정**입니다. `audit_review_claims.py`가 그 계측을 합니다.

## 3. Capacity — 이미 있고, Δw 기반을 추가했습니다

docstring에도 "초기 '전량 편입' 기준의 보수적 상한이며 정기변경 회전율은
이보다 작다"고 적혀 있습니다. 리뷰가 제안한 `|Δw|` 기반이 없었던 건 맞고,

## 6. 위성군 5% 상한 — 역산해보니 안전하지 않습니다

제안: "AUM 3,000억 이상 시 위성군 개별 비중 상한 5%"

같은 산식을 뒤집어 **5%가 실제로 며칠에 해당하는지** 계산했습니다
(`python analysis/capacity_v2.py --aum 3000`):

```
[역질문] 제안된 고정 상한 5% 는 며칠에 해당하는가?  (AUM 3000억)
 ADV60(억)   상한 5% 전량 매매 소요일
     15.0            100.0
     45.0             33.3
    120.0             12.5
    500.0              3.0
```

**ADV60 15억 종목이면 5% 상한에서도 100거래일**입니다. 리뷰가 예로 든
테크윙(ADV60 45억)도 33거래일입니다. 5%는 **안전해 보이는 숫자일 뿐
안전하지 않습니다.**

문제는 고정 퍼센트라는 형식 자체입니다. 같은 5%가 ADV에 따라 3일에서
100일까지 33배 차이가 납니다. 시장 유동성이 변하면 조문의 의미가 바뀌고,
그때마다 재량으로 숫자를 고치면 **재현성 원칙**이 깨집니다.

### 대안 — 허용일수를 고정하고 상한을 역산

```
w_max_i = ADV60_i × 참여율 × 허용일수 / AUM
```

허용일수(예: "정기변경은 5거래일 안에 소화한다")는 운영 목표라서 시장이
변해도 그대로입니다. 상한이 자동으로 따라옵니다.

```
 ADV60(억)  AUM(억)   3일     5일     10일    20일
     15      3000   0.15%   0.25%   0.50%   1.00%
     45      3000   0.45%   0.75%   1.50%   3.00%
    120      3000   1.20%   2.00%   4.00%   8.00%
    500      3000   5.00%   8.33%  16.67%  33.33%
```

이 표가 말해주는 더 중요한 사실: **AUM 3,000억에서 ADV 15억짜리 위성주는
어떤 상한을 걸어도 편입이 부담스럽습니다.** 상한을 조이는 게 아니라
**기초 유니버스 필터의 ADV 하한(현행 10억)을 올리는 것**이 더 근본적인
해법일 수 있습니다. 이것도 위원회 상정 사안입니다.

참고로 현행 조문은 이미 위성 개별 15% · 합계 18% 상한을 갖고 있습니다.
AUM 3,000억·ADV 15억 종목이 15%까지 차면 전량 매매에 300거래일 —
정기변경 주기(약 125거래일)보다 깁니다. **현행 상한도 재검토 대상**입니다.

## 4·5. 동의하는 항목

**4. DART PIT 자동화** — 이미 로드맵 1순위입니다. `hbm_evidence.py`에
`--fiscal-year` 추가가 최고 레버리지라는 판단도 같습니다.
LLM 파싱에 신뢰도 점수를 붙이고 사람 검수를 남기라는 제안에 동의합니다 —
판정값은 지수의 근간이라 조용한 오류가 가장 위험합니다.

**5. 생존편향** — 동의하고 이미 한계점에 신설했습니다.
다만 **"1.5~3.0%p 상향 왜곡"은 출처 없이 인용하지 마십시오.** 편향 크기는
유니버스·기간·업종마다 다릅니다. 실제로 대조해서 나온 값을 쓰거나,
"방향은 위쪽, 크기는 미측정"이라고 정직하게 쓰는 편이 강합니다.
