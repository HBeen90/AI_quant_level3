# "PIT 심사 스냅샷 13회분"이 정확히 무슨 말인가

## 0. 한 문장

지금 있는 건 **"2026년 7월에 규칙을 돌리니 7종목이 나왔다"** 한 장이고,
백테스트가 요구하는 건 **"2020년 6월에 그 규칙을 돌렸으면 뭐가 나왔을까"**
부터 13번의 답입니다. 그 13장을 만들 재료가 없습니다.

## 2. "스냅샷 한 장"이 정확히 뭔가

`build_event_schedule()`이 각 시행일에 받는 표 하나입니다. **후보 전원**이
행으로 들어가고(편입될 종목만이 아니라 탈락할 종목까지), 엔진이 그 표를 보고
편입/탈락을 스스로 판정합니다.

`data/snapshots/snapshot_20200615.csv` — 이런 모습입니다:

```csv
ticker,name,group,exposure,mem_ratio,float_mcap,eligible,탈락사유
005930,삼성전자,anchor,,,2.85e+14,True,
000660,SK하이닉스,anchor,,,4.71e+13,True,

0AAAAA,○○전자,core,0.12,0.44,3.10e+11,True,
0BBBBB,△△소재,satellite,0.15,0.72,1.80e+11,True,
0CCCCC,□□테크,core,0.55,0.61,2.20e+10,False,ADV60<10억
0DDDDD,◇◇반도체,satellite,0.09,0.81,4.40e+11,False,공정/위원회 미확인
...  (후보 33종목 전부)
```

| 컬럼 | 뜻 | 엔진이 이걸로 뭘 하나 |
|---|---|---|
| `exposure` | HBM 밸류체인 매출 / 전사매출 | 핵심군 판정 (신규 30% / 유지 27%) |
| `mem_ratio` | 메모리 반도체향 매출 / 전사매출 | 위성군 판정 (신규 70% / 유지 67%) |
| `float_mcap` | 유동시가총액 = 시총 × 유동비율 | 40/60 배분과 비중 상한 |
| `eligible` | 기초 유니버스 필터 통과 여부 | 하드 탈락 (버퍼보다 우선) |
| `group` | 어느 규칙으로 심사받는가 | 판정 규칙 선택 |

**핵심은 이 표의 값이 시점마다 달라야 한다는 것입니다.** 2020년 6월의
`exposure`와 2024년 6월의 `exposure`가 같으면, 그 사이에 아무 일도 안
일어난 게 됩니다.

## 3. "그럼 오늘 값을 13장에 복붙하면 안 되나?"

안 됩니다. 그리고 이건 의견이 아니라 실험으로 확인됩니다.
`analysis/demo_why_pit.py`가 **같은 엔진에 두 가지 입력**을 넣고 돌린 결과:

```
                     유지선  편입  편출  편출입 합  평균 종목수
FROZEN  none    0.30/0.70    0    0       0        18.0
        narrow  0.29/0.69    0    0       0        18.0
        mid     0.27/0.67    0    0       0        18.0
        wide    0.25/0.65    0    0       0        18.0
PIT     none    0.30/0.70   32   29      61        16.8
        narrow  0.29/0.69   28   24      52        17.5
        mid     0.27/0.67   21   15      36        18.7
        wide    0.25/0.65   18   12      30        19.2
```

**FROZEN(오늘 값 복사): 6년 동안 편출입이 0회입니다.**
판정값이 안 변하니 매 회차 같은 종목이 뽑히고, 버퍼 정책 4안이 **전부 똑같은
답**을 냅니다. 회전율 0, 정책 간 차이 0.

이게 왜 치명적이냐면:

- 방법론 3장 "성과 보고"의 **연율화 회전율이 0**으로 나옵니다. 정기변경마다
  비중만 조금 조정되고 종목은 그대로니까요.
- **버퍼룰이 "아무것도 안 한 것"으로 측정됩니다.** 27/67을 25/65나 29/69와
  비교할 근거가 애초에 생성되지 않습니다. PR 노트 미결 1번을 못 닫습니다.
- 백테스트는 에러 없이 끝나고 예쁜 그래프도 나옵니다. **측정하는 게 없을
  뿐입니다.** 이게 가장 위험한 형태의 실패입니다 — 실패한 티가 안 납니다.

**PIT: 편출입 30~61회, 정책마다 다릅니다.** 버퍼를 넓힐수록 61→30회로
줄어들고, 그 감소분이 곧 매매비용 절감입니다. 그 대가(적합도 하락)와
맞바꾸는 표가 27/67 채택의 근거가 됩니다. 정확히 지금 필요한 그 표입니다.

데모에서 실제로 움직인 내역(PIT/mid):

```
       시행일   n                          편입              편출
2021-06-14  17  B00002,B00004,B00006,...   B00005,T00001,...
2023-06-12  20  B00006,G00001,G00003,...   T00001,T00003
2024-06-17  21  G00002,T00001,T00003       T00002,T00004
2025-06-16  21  G00004,T00002,T00004       B00005,T00001,...
```

- `G*` = **성장형**. HBM 붐 전에는 노출도 12~19%라 미편입이었다가
  2023년경 임계값을 넘어 편입됩니다. **테마 지수의 서사가 바로 이겁니다.**
  오늘 값을 고정하면 이 종목들이 2020년부터 편입돼 있던 것으로 그려지고,
  "HBM 테마를 포착하는 지수"라는 주장 자체가 백테스트로 증명이 안 됩니다.
- `B*/T*` = **경계 진동**. 30%/70% 근처에서 오르내립니다. 버퍼룰이 존재하는
  이유가 이 종목들이고, 이들이 안 움직이면 버퍼룰 검증이 불가능합니다.

## 4. 그래서 실제로 채워야 하는 건 뭔가

스냅샷 13장을 손으로 만드는 게 아닙니다. **판정 원장 CSV 하나**를 채우면
`build_pit_snapshots.py`가 13장을 생성합니다.

원장 1행 = **(종목 하나, 사업연도 하나)**의 판정입니다.

```csv
ticker,name,disclosed_at,fiscal_year,sector,hbm_massproduction,hbm_exposure,mem_ratio,process_confirmed,committee_ok,free_float,source,audit_opinion,admin_issue,reviewer,judgment_status
000001,예시기업,2026-03-20,2025,반도체장비,FALSE,0.35,,TRUE,FALSE,0.60,DART 접수 URL TODO,적정,FALSE,,DRAFT
```

컬럼별로 **누가 어디서 채우는가**:

| 컬럼 | 출처 | 자동화 |
|---|---|---|
| `disclosed_at` | 사업보고서 공시일 | ✅ DART API |
| `fiscal_year` | 사업연도 | ✅ |
| `hbm_exposure` | 사업보고서 「매출 및 수주상황」 제품별 매출 | ⚠️ **근거 수집만 자동, 숫자는 사람** |
| `mem_ratio` | 같은 표 + IR 자료 | ⚠️ 동일 |
| `hbm_massproduction` | 양산·공급계약 공시 | ⚠️ 동일 |
| `process_confirmed` | TSV·하이브리드본딩 귀속 매출 문서 | ⚠️ 동일 |
| `committee_ok` | 위원회 확인 (①②의 문서 충족 확인만) | 사람 |
| `free_float` | DART 최대주주+자기주식 차감 | ✅ 반자동 |
| `audit_opinion`, `admin_issue` | 해당 시점 감사·관리종목 상태 | ✅ 반자동 + 사람 확인 |
| `source`, `reviewer`, `judgment_status` | 계보·책임·확정 상태 | 사람 (`FINAL`) |
| 시총·거래대금·상장경과 | pykrx | ✅ **완전 자동** (원장에 안 씀) |

`hbm_evidence.py`가 이미 ⚠️ 항목의 **근거를 차려주는 일**(매출표 추출 +
HBM 키워드 문장 수집 + 수주공시 제목)을 합니다. 과거 원장을 만들 때는
`--fiscal-year`를 지정하면 해당 연도 사업보고서만 조회하고 현재 IR·관리종목
정보의 자동 혼입을 막습니다.

## 5. 실제 작업량 — 생각보다 적습니다

**"13시점 × 33종목 = 429번 판정"이 아닙니다.**

사업보고서는 연 1회(3월)만 나옵니다. 그래서 6월 심사와 12월 심사는 **같은
사업연도 자료**를 봅니다(시가총액만 다름). 데모에서 편출입이 전부 6월에만
일어난 이유가 이것입니다.

```
이론적 최대 : 33종목 × 7사업연도(FY2019~FY2025) = 231행
```

여기서 더 줄어듭니다:

| 후보 유형 | 대략 종목 수 | 필요한 행 | 이유 |
|---|---|---|---|
| 앵커 (삼성전자·SK하이닉스) | 2 | 각 1~2행 | `hbm_massproduction=TRUE` 고정. 노출도 안 봄 |
| 명백 미달 (전 구간 10%대) | ~8 | 각 1행 | 한 번 확인하면 전 구간 미편입 |
| 안정 편입 (전 구간 50%+) | ~5 | 각 2~3행 | 임계값에서 멀어 정밀도 불필요 |
| **성장형·경계 진동** | **~15** | **각 7행** | **여기가 진짜 작업** |
| 위성 후보 | ~3 | 각 3~4행 | |

**실질 작업량 ≈ 120~140행, 그중 정밀도가 중요한 건 15종목 × 7년 ≈ 105행.**

`as_of_ledger()`가 공시일 기준으로 13시점 매핑을 자동으로 해주므로,
원장에 없는 시점은 자동으로 직전 사업연도 값이 쓰입니다. **행을 안 채우면
누락이 아니라 "직전 판정 유지"로 처리됩니다.**

지금 바로 이 명령으로 필요한 행 목록을 뽑을 수 있습니다:

```powershell
python analysis/build_pit_snapshots.py --ledger data/verdict_ledger.csv --template-only
```

## 6. 작성 범위를 단계적으로 늘리는 방법

### 1단계: 2026-07-23 확정 횡단면 — 완료
33종목 한 시점의 판정값을 확정해 현재 판정 규칙과 비중 산정을
재현했습니다(7종목, 최대 비중 오차 0.001302%p). 이 자료는 여러 공개
자료를 2026-07-23에 종합한 판정 단면이며, 사업연도별 원장은 아닙니다.
시계열이 아니므로 CAGR·MDD·회전율을 산출하지 않습니다.

### 2단계: 연속 사업연도
우선순위 종목의 연속된 사업연도를 채워 관측 가능한 구간만 백테스트합니다.
비어 있는 연도는 선형 보간하거나 현재 값을 복사하지 않습니다. 커버리지 부족은
결과와 함께 보고합니다.

### 3단계: Full
33종목의 FY2019~FY2025 223행과 과거 상장폐지·피합병 후보까지 채웁니다.
이 단계에서만 2020~2026 전 구간 성과와 버퍼 정책을 정식 실측으로 보고합니다.

부분 원장은 데이터 품질 점검과 횡단면 재현에 유용하지만, 없는 관측치를
채워 넣어 긴 시계열 성과처럼 보이게 만들지는 않습니다.

## 7. 빠뜨리면 안 되는 것 하나 — 생존편향

후보 33종목은 **2026년 시점에 살아있는 종목**으로 뽑혔을 겁니다. 그러면
2020~2025 사이에 상장폐지·피합병된 HBM 관련 종목이 통째로 빠집니다.
망한 종목이 빠진 채로 6년 성과를 재면 **성과가 위로 편향**됩니다.

이건 코드가 못 찾습니다. `run_backtest.listing_check()`가 "이 종목이 그
시점에 상장돼 있었나"는 확인해 주지만, **"그 시점엔 있었는데 지금 없는
종목"은 사람이 찾아야** 합니다. KRX 상장폐지 목록에서 2020~2026 반도체
업종을 훑어 후보 원장에 추가하면 됩니다.

찾아서 0종목이면 그것도 결과입니다. **"찾아봤고 N종목 해당하며 편향 방향은
위쪽"**이라고 말할 수 있으면, 발표에서 가장 아픈 질문 하나가 막힙니다.

```powershell
# 1) 논리 확인 — 왜 이 데이터가 필요한지 직접 눈으로 (30초, 데이터 불필요)

python build_ledger_from_evidence.py --scaffold data\verdict_ledger_scaffold.csv --evidence evidence\judgment_input_draft.csv --fiscal-year 2025 --allow-provisional --out data\verdict_ledger_provisional.csv
```
